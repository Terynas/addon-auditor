# SV001: SavedVariables used at file scope (before they load)

**Category:** savedvars

## Why

WoW executes an addon's Lua files first, then runs its SavedVariables file (which assigns the saved tables to the globals), then fires `ADDON_LOADED`. At file scope `MyAddonDB` is therefore always nil: `MyAddonDB = MyAddonDB or {}` builds a throwaway placeholder that the saved table replaces a moment later. That alone is harmless, but anything that captures it (`local db = MyAddonDB`), writes defaults into it, or passes it to a migration operates on the placeholder, so settings seem to reset every login (`warn`). A lone file-scope `X = X or {}` with no runtime initialisation anywhere is reported as `info`. Note: the First Timers note says the file-scope pattern works because SVs are parsed first; that is only true with `## LoadSavedVariablesFirst: 1`, which suppresses this rule.

## Bad

```lua
MyAddonDB = MyAddonDB or {}
local db = MyAddonDB
if db.scale == nil then db.scale = 1 end
print(db.scale)
```

## Good

```lua
local addonName, ns = ...
local f = CreateFrame("Frame")
f:RegisterEvent("ADDON_LOADED")
f:SetScript("OnEvent", function(self, event, loaded)
  if loaded ~= addonName then return end
  MyAddonDB = MyAddonDB or {}
  if MyAddonDB.scale == nil then MyAddonDB.scale = 1 end
  ns.db = MyAddonDB
  self:UnregisterEvent("ADDON_LOADED")
end)
```
